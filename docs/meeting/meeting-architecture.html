01

왜 검증기가 따로 있어야 하나

이 프로젝트의 모든 설계 결정이 여기서 나온다.

실제로 돌려 본 예시다. 연결 코드를 절반만 고친 상태에서 검증기를 통과시키면 이런 결과가 나온다. 

$ api-doctor run -d seoul_library -c connector_partial.py

✓  execution     후보가 4건을 반환했습니다.
✓  fields        4건에서 필수 필드가 보존되었습니다.
✓  values        2개 값 규칙을 만족합니다.
✗  completeness  누락 1건; 건수 4 != 기대 5

verification_failed

앞의 세 검사가 전부 통과한다. 코드는 실행되고, 필드도 멀쩡하고, 값도 규칙에 맞는다. 네 번째 검사만 실패한다. 마지막 레코드 하나가 조용히 빠졌기 때문이다. 사람이 "고쳤다"고 판단하기 딱 좋은 상태이고, LLM이 "수정 완료"라고 보고하기도 딱 좋은 상태다.

이 제품을 지배하는 한 문장: LLM은 어디로 갈지만 정하고, 무엇이 참인지는 LLM이 없는 코드가 정한다.

에이전트를 다섯으로 나눈 것도, 검증기를 분리한 것도, 도구를 게이트웨이 뒤에 둔 것도 전부 이 문장에서 파생된다.

대상 문제의 구체적 형태

서울 열린데이터광장의 SeoulPublicLibraryInfo를 대상으로 삼았다. 실제로 호출해 확인한 이 API의 특성이 문제를 만든다.

  • 응답이 서비스명으로 한 겹 감싸져 있다. 레코드 배열은 SeoulPublicLibraryInfo.row에 있고 최상위 row는 없다. 최상위에서 찾는 코드는 예외 없이 빈 배열을 얻는다.
  • 페이지가 query 파라미터가 아니라 경로의 범위다. /{KEY}/json/서비스/{시작}/{끝}/ 형태이고 1부터 시작해 양끝을 포함한다.
  • list_total_count는 서비스 전체 건수다. 이번 요청의 건수가 아니다. 종료 조건을 여기에 걸면 틀어진다.
  • /json/으로 요청해도 오류는 XML로 온다. 그래서 response.json()이 던지는 예외가 파싱 버그가 아니라 서버 측 거절일 수 있다.

대표 데모는 이 중 두 가지가 겹친 복합 결함이다 — 중첩 경로를 잘못 읽고, 범위 종료 조건도 틀려서, 실행은 되는데 0건이 나온다.

02

아키텍처 한 장

1차 분할 단위는 컴포넌트가 아니라 신뢰 영역이다. 경계를 넘는 것은 좁고 명시적인 계약뿐이며, 경계는 프롬프트가 아니라 프로세스·파일권한·컨테이너로 강제한다.

Zone T · 신뢰 영역 (LLM 없음) Zone A · 에이전트 (LLM) Zone S · 격리 실행 굵은 화살표 = 강제 통과 지점

경계별로 무엇이 통과하고 무엇이 막히나

경계통과 가능절대 불가강제 수단
U → T파일 경로, dataset_id, query, 취소 시그널임의 실행 인자, 경로 탈출, 심볼릭 링크경로 정규화 + 루트 하위 검사
T → A발췌된 근거, 중립 objective, 예산 임대API key, 기대값, 원본 쓰기 핸들, 파일시스템도구 화이트리스트 + 가시성 매트릭스
A → T9종 도구 호출, 구조화 반환정책 변경, 예산 재설정, 최종 상태 쓰기도구 스키마 + request_finish는 예약만
T → Scandidate.py (읽기 전용), 동결 응답API key, 호스트 FS, 네트워크, 정답--network none + ro mount + cap drop
S → T반환 레코드, 제한된 stdout, 차단 기록임의 파일 쓰기, 외부 연결컨테이너 정책 + 출력 크기 상한

핵심 불변식: Zone A는 Zone S에 직접 닿지 않는다. 수리 에이전트도 submit_patch로 후보를 만들 뿐이고, 실행은 도구 게이트웨이가 예산을 차감한 뒤 Zone T가 수행한다.

03

처음부터 끝까지: 실제로 무슨 일이 일어나나

아래는 실제 모델(nvidia/nemotron-3-super-120b-a12b)로 돌린 verified_repaired 실행을 단계별로 푼 것이다. 지어낸 흐름이 아니다.

초록 구간은 모델을 한 번도 부르지 않는다 · 주황 구간에서만 LLM 이 개입한다
  1. 입력

    사용자가 깨진 연결 파일을 건넨다

    CLI가 입력을 검사한다. Python 파일 1개(100KB 이하), fetch_records(http, query) 서명 확인, 그리고 코드에 원문 키처럼 보이는 문자열이 있으면 모델에 보내기 전에 거절한다.

    $ api-doctor run -d seoul_library -c connector_broken.py
  2. prepare

    격리 경계를 먼저 확인한다

    후보 코드를 한 줄이라도 돌리기 전에 샌드박스 backend가 경계 자가검사 5종을 통과해야 한다. 통과하는 backend가 없으면 호스트에서 대신 실행하지 않고 RUNTIME_UNAVAILABLE로 끝난다. 코드베이스에 HostBackend는 존재하지 않는다.

  3. baseline

    원본을 격리 실행하고 고정 검증기가 판정한다

    이 시점까지 모델은 한 번도 호출되지 않는다. 원본이 이미 계약을 만족하면 여기서 verified_unchanged로 끝난다 — 모델 호출 0회. 인증 오류·제공기관 장애도 신뢰된 분류기가 여기서 잡아 모델 없이 중단한다.

    ✓ execution     후보가 0건을 반환했습니다.
? fields        레코드가 0건이라 확인할 수 없습니다 (기대 5건).
? values        레코드가 0건이라 확인할 수 없습니다 (기대 5건).
✗ completeness  누락 5건; 건수 0 != 기대 5

    0건일 때 필드·값을 "통과"로 적지 않고 확인 불가로 판정한다. 그러지 않으면 아무것도 안 하는 코드가 4개 중 3개 초록으로 보인다.

  4. delegating

    런타임이 1+4 팀을 구성하고 도구 인벤토리를 실측한다

    deepagents로 팀을 만들되, 기본으로 딸려오는 execute(셸)·write_file·delete 등은 도구 노드에서 제거한다. 그리고 컴파일된 그래프의 실제 도구 목록을 순회해 확인한다. 하나라도 어긋나면 실행하지 않는다.

    main                   ['get_budget','read_evidence','read_file',
                        'request_finish','request_stop','task']
spec_researcher        ['get_budget','read_evidence','search_spec']
runtime_diagnostician  ['get_budget','inspect_code','inspect_trace',
                        'read_evidence','run_probe']
repair_engineer        ['get_budget','inspect_code','read_evidence',
                        'run_probe','submit_patch']
data_auditor           ['get_budget','inspect_code','inspect_trace',
                        'read_evidence','run_probe']

위험 도구 누수: 없음 · 하위 재위임 가능 역할: 없음
  5. ① 명세

    main이 명세 조사를 위임한다

    모든 역할을 한 번씩 부르지 않는다. main이 필요한 조사만 고른다. 명세 조사자는 등록된 스킬 자료만 볼 수 있고 원격 문서를 새로 가져올 수 없다.

    → "The Seoul Library API returns a JSON object wrapped by the service name 'SeoulPublicLibraryInfo'. The record array is at SeoulPublicLibraryInfo.row."

  6. ② 진단

    진단자가 실제 요청·응답을 관측한다

    run_probe로 후보를 돌리고 inspect_trace로 실제 오간 요청과 응답 본문을 본다. 인증키 자리는 {KEY}로 치환돼 있다.

    경로: /{KEY}/json/SeoulPublicLibraryInfo/1/2
응답: {"SeoulPublicLibraryInfo": {"list_total_count": 216,
       "RESULT": {"CODE": "INFO-000", ...}, "row": [...]}}

    → "The candidate returns 0 records because it looks for a top-level 'row' key that does not exist, and it only requested positions 1-2 of the contract range 1-5."

  7. ③ 수리

    수리자만 코드를 바꾼다

    원본은 건드리지 않는다. 복사된 후보 파일의 새 버전을 만들고 최대 2버전이다. 수리자가 남긴 설명은 감사자에게 전달되지 않는 가시성으로 저장된다.

    → "Fixed JSON path to SeoulPublicLibraryInfo.row and implemented pagination loop over start/end range."

  8. ④ 감사

    감사자가 독립적으로 손실을 조사한다

    런타임이 중립 템플릿으로 작업 봉투를 새로 조립한다. main이 쓴 objective조차 덮어쓰고, 수리자의 설명도 main의 대화도 넣지 않는다. 감사자는 설명을 믿는 대신 직접 관측해야 한다.

    계약이 요구하는 각 위험 영역마다 probe를 실제로 돌리고 {가설, 불변식, probe_result_id, 결론}을 반환한다.

    page_partition  ✓ 구간 크기를 바꿔도 같은 5건이 나왔습니다.
field_presence  ✓ 5건에서 식별키가 관측되었습니다.

audit_coverage: remaining_risks = []
  9. 게이트

    종료 게이트가 판정한다 — 우회 불가

    main의 종료 요청, 일반 텍스트 종료, agent 예외, 루프 상한이 전부 여기로 수렴한다. 판정 함수는 불리언 넷의 논리곱이며 LLM 출력을 인자로 받지 않는다.

    {'no_forced_halt': True,        ← 강제 중단이 없었는가
 'fixed_check_passed': True,   ← 현재 hash 의 고정 검증
 'audit_complete': True,       ← 현재 hash 의 감사 완료
 'no_unresolved_findings': True}

verified_repaired

    패치가 바뀌면 이전 감사는 3-hash 키가 어긋나 자동으로 만료된다. 별도 만료 로직이 없다 — 조회가 실패할 뿐이다.

  10. 기록

    모든 것이 재생 가능하게 남는다

    runs/<run_id>/
├── events.jsonl          append-only · 재생의 유일한 입력
├── manifest.json         events 에서 파생된 스냅샷
├── candidates/           original.py · v1.py · v2.py
├── checks/               3-hash 로 키가 잡힌 검사 결과
├── evidence/             관측(observation)과 주장(assertion)을 구분
├── denials.jsonl         격리 차단 기록 (backend_id 필수)
├── profiling/            역할별 호출·토큰·지연 + Gantt
└── report.md / .json

    api-doctor replay는 모델·API·코드 실행 0회로 기록을 재생한다. 이것은 런타임 플래그가 아니라 의존성 부재로 보장된다 — replay 경로는 model/·sandbox/·data/를 import하지 않으며 테스트가 이를 검사한다.

04

왜 신뢰 영역으로 나눴나

에이전트를 여러 개 두는 것보다 이 분할이 먼저다.

멀티 에이전트 시스템에서 흔한 실패는 "여러 모델이 서로를 승인하는 것"이다. 감사자가 또 하나의 승인 버튼이 되면 역할을 나눈 의미가 없다. 그래서 판정 권한 자체를 모델에서 떼어냈다.

Zone T

신뢰 영역

레지스트리·계약·기대값·브로커·검증기·예산 원장·사건 기록. LLM이 없다. 여기서 내린 판정만 최종이다.

Zone A

에이전트 영역

main + 4 전문가. 도구 게이트웨이를 통해서만 말한다. 파일시스템도 셸도 없다. 어디로 갈지만 정한다.

Zone S

실행 영역

후보 코드가 도는 곳. 네트워크 없음, 비밀값 없음. 좁은 IPC로만 브로커에 요청한다.

감사 독립성은 "다른 모델"이 아니다

감사자가 받는 것은 런타임이 새로 조립한 중립 봉투다 · main 이 쓴 objective 조차 덮어쓴다

감사자도 같은 무료 모델을 쓴다. 독립성은 입력을 다르게 주는 것으로 만든다. 증거 저장소가 visibility 필드로 강제한다.

자료main명세진단수리감사검증기
공식 문서 발췌요약✓✓전달분✓—
현재 후보 코드hash만✕✓✓✓✓
수리자의 설명✓✕✕✓✕✕
main 전체 대화✓✕✕✕✕✕
도구 관측 원문요약해당분해당분자기분✓✓
기대값 · 정답✕✕✕✕✕✓
API key✕✕✕✕✕브로커만

증거마다 kind ∈ {observation, assertion}이 붙는다. 모델이 만든 것은 전부 assertion이며, assertion을 인용해도 관측으로 승격되지 않는다. 종료 게이트는 observation 근거가 없는 finding 해소를 거절한다.

05

1+4 팀: 각자 무엇을 할 수 있고 무엇을 못 하나

역할 분리는 프롬프트가 아니라 도구 목록과 가시성으로 만든다.

main

recovery_lead

조사 순서·담당자·질문을 정하고, 근거가 어긋나면 좁힌 질문으로 재위임한다.

  • 못 하는 것: 코드 쓰기, 직접 실행, 계약 변경, 성공 확정
  • request_finish는 검증을 예약할 뿐이다
  • 같은 역할·질문·후보로 재위임하면 거절된다
서브 1

spec_researcher

공식 자료에서 응답 구조·조회 규칙·오류 구별 방법을 찾는다.

  • 도구: search_spec · read_evidence
  • 샌드박스도 코드도 만지지 못한다
  • 원격 문서를 즉석에서 가져올 수 없다 — 사전 검토된 스킬 자료만
서브 2

runtime_diagnostician

코드의 어느 지점에서 실패·손실이 생기는지 관측으로 좁힌다.

  • 도구: run_probe · inspect_trace · inspect_code
  • 후보를 고치지 못한다
  • 실행이 성공해도 데이터는 빠질 수 있다는 전제로 본다
서브 3

repair_engineer

확인된 원인에 맞춰 최소 변경을 만든다. 이 역할만 코드를 바꾼다.

  • 도구: submit_patch · inspect_code · run_probe
  • 최대 2버전 · 원본·계약·기대값은 바꿀 수 없다
  • 예외를 삼키거나 빈 배열로 "통과"시킬 수 없다 — 검증기가 전체성을 본다
서브 4

data_auditor

수리 설명 없이, 코드와 관측만 보고 데이터가 빠질 가능성을 조사한다.

  • 도구: run_probe(허용된 catalog만) · inspect_trace
  • 성공을 확정할 권한이 없다
  • probe를 돌리지 않고 "문제 없음"이라 하면 거절된다
비에이전트

고정 검증기 + 종료 게이트

변경 불가능한 기준으로 실행·필드·값·전체성을 검사하고 최종 판정을 내린다.

  • 모델의 주장·감사자의 찬성·main의 종료 요청은 입력이 아니다
  • verify/가 agents/를 import하면 CI 실패

하위 재위임이 구조적으로 불가능하다. 위임 수단(task)은 main만 갖는다. 전문가에게는 그 도구가 애초에 발급되지 않으므로, 프롬프트를 아무리 바꿔도 다른 에이전트를 부를 수 없다. task가 나열하는 대상도 등록된 넷뿐이고 general-purpose는 꺼져 있다.

06

무엇이 "고쳤다"를 결정하나

네 검사를 매번 전부 수행한다. 감사자가 고른 probe는 추가 조사이며 필수 검사 수를 줄일 수 없다.

검사무엇을 보나없으면 생기는 일
execution후보가 실행되고 list[dict]를 반환했는가예외가 곧 실패라고만 판단

종료 게이트의 네 단계

순서가 곧 우선순위다 · 어느 단계에서 걸리든 성공으로 승격되지 않는다

probe의 불변식은 정답 없이 검사 가능해야 한다

감사자는 기대값을 볼 수 없다. 그런데도 손실을 관측해야 한다. 그래서 probe의 불변식을 비공개 기대값 없이 검사 가능한 성질로 설계했다.

probe불변식정답 없이 어떻게 판정하나
page_partitionpartition_invariance구간 크기를 2와 3으로 바꿔 돌려 같은 식별키 집합이 나오는지 본다. 몇 건이 정답인지 몰라도 어긋남이 드러난다

공허한 성립을 걸러낸다. 0건을 반환하는 후보는 "구간을 바꿔도 같은 0건"이라 분할 불변식이 성립해 버린다. 그것을 통과로 세면 아무것도 안 하는 후보가 감사를 통과한다.

그래서 VACUOUS 결과를 따로 두고, 위험 영역을 덮은 것으로 세지 않는다.

후보 코드를 돌리기 전에 매번 확인하며, 하나라도 실패하면 실행하지 않는다.

read_host_secret 검사는 호스트 프로세스에만 존재하는 canary 환경변수를 심어, 그것이 컨테이너 안에서 보이지 않음을 적극적으로 증명한다. 이미지가 원래 갖고 있는 환경변수는 baseline과 비교해 제외하므로 오탐이 없다.

OpenShell은 이 기기에서 쓸 수 없다. Linux 대상인데 개발기가 macOS다. 컨테이너 대안으로 내려가되, 컨테이너 결과를 OpenShell 증거로 표시하는 것이 코드 수준에서 불가능하게 막았다 — 모든 차단 기록에 backend_id가 필수이고, 보고서 생성기가 이를 분리한다.

08

실제 모델이 드러낸 것들

scripted 모델로는 전부 통과하던 구조가 실모델에서 무너졌다. 이 목록이 이번 작업에서 가장 값진 산출물이다.

통합 버그

main이 위임을 한 번도 하지 않았다

프롬프트가 자체 하네스 형식({"action":"delegate"})을 가르치는데 deepagents에서는 task 도구를 호출해야 한다. scripted 테스트는 task 형식을 썼기 때문에 이 불일치가 드러나지 않았다.

통합 버그

모델이 probe ID를 지어냈다

deepagents는 서브에이전트에게 task의 description만 전달한다. 자체 하네스가 작업 봉투로 주던 계약·probe 목록이 전달되지 않아 UNSUPPORTED_PROBE가 3번 났다. 팀 구성 시점에 시스템 프롬프트로 구워 넣어 해결했다.

명세 미구현

inspect_trace가 응답을 반환하지 않았다

설계는 "정제한 요청·응답·오류"인데 요청만 구현돼 있었다. 그래서 진단 역할이 실제 응답 구조를 볼 방법이 없었고, 깨진 후보가 0건을 돌려주면 "실제 응답이 어떻게 생겼는지"를 되물으며 위임 3회를 태웠다.

프레임워크

자동 요약이 main 예산을 먹고 있었다

deepagents가 기본 스택에 요약 미들웨어를 넣고 main의 모델로 요약을 돌린다. 원장에는 main 호출로 잡히지만 용도가 구분되지 않아, 조사 예산이 요약에 소진되고 감사 전에 멈췄다. 끄자마자 verified_repaired에 도달했다.

설계 긴장

중복 위임을 무조건 막으면 적응성이 사라진다

문구만 바꾼 재위임이 예산을 태웠다. 그러나 무조건 막으면 "감사가 문제를 찾아 명세를 다시 확인하는" 경로까지 사라진다. 수리·감사가 아직 남은 동안에만 조사 반복을 막는 것으로 해결했다.

모델 특성

추론 토큰이 출력 예산을 함께 쓴다

이 모델은 reasoning 모델이라 사소한 JSON 한 줄에도 출력 258토큰이 나갔다. 추론이 상한을 다 쓰면 본문이 잘려 오는데, 잘린 응답을 정상처럼 돌려주면 상위에서 "형식 위반"으로 오인한다. 명시적 오류로 올리도록 고쳤다.

측정 자체가 틀렸던 적도 있다

검출 평가의 첫 판은 최종 상태로 판정했다. 그런데 모델 키가 없으면 결함 사례가 전부 needs_user_action으로 끝나므로, 실제로는 "결함 검출"이 아니라 "키 없음"을 재고 있었다.

고정 검증기가 baseline에서 내린 판정으로만 재도록 바꾸자 비로소 의미 있는 수치(정상 훼손 0, 거짓 성공 0)가 나왔다.

평가가 실제 버그를 두 개 찾아냈다

  • 동결 자료에 없는 범위 요청이 policy_blocked로 끝났다. 허용 밖 endpoint는 정책 위반이지만, 범위를 잘못 계산한 것은 고칠 수 있는 코드 결함이다. 둘을 같이 다루면 복구 가능한 버그가 복구 불가로 종료된다.
  • 파일시스템 차단이 기록되지 않았다. 네트워크 시그니처만 보고 있었다. 읽기 전용 rootfs·권한 거부도 차단 기록으로 승격하도록 고쳤다.

경계 사례 하나는 설계 자체가 틀렸다. 컨테이너 자신의 /etc/passwd를 읽는 것은 호스트 유출이 아니라 막을 것도 없다. 실제로 막히는 동작(읽기 전용 경계 밖 쓰기)으로 교체했다.
